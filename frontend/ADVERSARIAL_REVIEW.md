# SciExchange frontend: adversarial review

Date: 2026-10-22 (Asia/Singapore). Branch: `frontend`. Scope: Member C-owned frontend, its mock protocol model, API boundary and browser workflows. This checkout contains no backend implementation; this is not a backend security assessment or proof of correct settlement.

## First-principles invariants

1. **Credit conservation:** opening allocation + accepted rewards − confirmed debits = available balance, which cannot be negative. Neither a button nor a caller-supplied price creates money.
2. **Authorization before delivery:** HTTP 402 is a challenge, not a successful purchase or data payload. A receipt input is not proof of payment. Only a successful, structurally validated backend response confirms live delivery.
3. **Binding:** a challenge belongs to a slice; a proposal binds both slices and their current attestations; approvals belong to an exact agreement. One PI approval cannot settle the simulated protocol.
4. **No contradictory trust:** a newly rejected slice cannot reuse a stale catalog badge to purchase, barter, stake or display a successful provenance chain.
5. **Race safety:** repeated requests cannot mint duplicate credit or charge twice in the mock ledger. Reset cannot resurrect an earlier transaction. Late reads cannot overwrite newer wallet state.
6. **Honest evidence:** simulated results are labeled. A configured service is not a confirmed healthy connection. CSV parsing, chart rendering and frontend metadata checks are not scientific or cryptographic proofs.

## Backend decisions still required from owners

The mock ledger represents one workspace buyer wallet. It does not model multiple laboratory identities, seller balances, merchant settlement or fees; the outbound purchase is recorded as a debit to the displayed demo vault payee. This is not a multi-account token-economy implementation.

Member A must define authenticated wallet identity and balance, how to obtain/confirm a SciCredit microtransfer, receipt binding to slice/nonce/price/payer, expiry and replay rules, transaction idempotency, and recovery after payment succeeds but delivery fails. These are requirements for the real service, not newly invented REST routes. A verifiable payload digest/content binding and larger/alternative tensor formats also need agreement. The frontend currently accepts numeric matrix JSON or numeric-column CSV up to 10 MB.

Member A must also confirm the provisional attestation/proposal schemas, current signature states, secure signer integration, reset authorization and CORS-exposed x402 headers. Member B must confirm authorized catalysis/battery analysis requests and responses. Shared contracts, backend code, data and other branches were not modified.
